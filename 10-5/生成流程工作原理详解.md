## 第 0 章 预备知识：Node-RED 的 5 个概念

Node-RED 是"数据流编程"：节点（node）之间用线（wire）连接，数据以消息（msg）的形式在线里流动。

| 概念 | 说明 | 本项目里的例子 |
|---|---|---|
| `msg` | 流动的数据包裹，是个 JS 对象 | 每轮采集就是一个 msg |
| `msg.payload` | msg 的主数据字段（最重要的约定） | 块读结果、契约报文都放在这 |
| `msg.topic` | msg 的主题字符串 | 块合并时标记"这是第几块"（block00/block01） |
| 节点 | 处理单元：输入 msg → 做点事 → 输出 msg | inject/change/switch/join/MQTT… |
| 配置节点 | 不进画布流程的共享配置（连接参数等） | MC 连接、MQTT broker、PG 库 |

记住这三个最常用的核心节点，全系统 80% 的逻辑靠它们：

- **inject**：定时器，每隔 N 毫秒发一个 msg（"上班打卡机"）；
- **change**：改 msg 的字段（本项目用它写 JSONata 表达式做数据装配）；
- **switch**：按条件分流（"安检门"，符合规则的往左，不符合的往右）。

## 第 1 章 全景：一条采集支路长什么样

每台 PLC 一个独立标签页（如 `EL_采集_123`），页面内是一条自左向右的流水线：

```
                    ┌──────── 采集与装配（蓝区）────────┐
 inject(轮询) ──→ MC Read(块1) ──→ 块内装配 ──┐
                └→ MC Read(块2) ──→ 块内装配 ──┤
                    (每块还有一条失败标BAD支路) │
                                              join(合并) ──→ 契约装配 ──→ 有值才报 ─┐
                    └──────────────────────────┘                              │
                                                                                ▼
                    ┌──────── 上报与计数（绿区）──────────────────────────┐
                    │ MQTT 上报 / PG SQL → 写库 → 成功计数 / 通信状态上报 / 数据出口 │
                    └──────────────────────────────────────────────────┘
                    ┌──────── 告警与异常（红区）──────────────────────────┐
                    │ 错误脚 → 告警限速 → 告警报文 → MQTT 告警             │
                    │ 错误脚 → 重连限速 → 重连指令 ──→ 回接首个 MC Read    │
                    └──────────────────────────────────────────────────┘
```

**一句话**：定时触发 → 分块读 PLC → 每块装配成点位数组（失败就造 BAD 空块）→ 合并 → 拼成标准报文 → 分四路发出去。

## 第 2 章 逐节点详解（采集与装配区）

### ① inject「[设备名] 轮询」
- **干什么**：每 N 毫秒（设备表里的扫描周期）发出一个 msg，启动一轮采集；
- **看点**：`repeat` 字段就是周期；周期 <1 秒时是"一次性 inject + delay 自循环"（亚秒模式，见第 6 章）；
- **新人误区**：inject 的 payload 是时间戳，没用——它只是发令枪，真正读数靠后面的节点。

### ② MC Read「[设备名] 读 D100,4」
- **干什么**：通过 MC 协议（三菱 PLC 专用）读一块寄存器；
- **地址串怎么读**：`D100,4` = 从 D100 开始连续读 4 个字（D100~D103）；`DFLOAT110,2` = 从 D110 读 2 个 FLOAT（占 4 字）；`M200.3,4` = 从 M200 的第 3 位起读 4 个位；
- **两个输出**：输出1（上）= 成功，payload 是 `{地址: 值}` 对象，如 `{D100: 5771, D101: 851, D102: 1234, D103: 900}`；输出2（下）= 失败（断线/超时/地址错），msg 走向失败支路；
- **为什么有多个**：点位表被生成器按"寄存器类型 + 地址连续性"合并成若干块，一块一个 MC Read。连续 100 个点 = 1 块；跳址（D1/D3/D5…）由"空洞容忍"参数把空洞也读回来，避免一块一点炸出几百个节点。

### ③ change「块内装配」
- **干什么**：把 `{D100: 5771, ...}` 翻译成点位数组 `values[]`；
- **翻译规则**（JSONata 表达式，双击节点可见）：每个登记过的点位取 `payload["D100"]` 这样的值，做工程值换算（linear 型：`工程值 = 原始值 × 斜率a + 偏移b`），并打质量码：
  - 取到值 → `quality: "GOOD"`；
  - 块成功但该点位没读到 → `UNCERTAIN`；
- **multi 块时**还会写 `topic = block00/block01…`（join 靠它认块）。

### ③' change「块N失败标BAD」
- **干什么**：该块读取失败时，造一块"全 BAD 空值"（`raw_value=null, eng_value=null, quality="BAD"`）；
- **为什么必须有它**：没有它，某块失败时下游 join 就永远缺一块、这一轮数据就静默丢了。**丢数据不可怕，可怕的是没人知道丢了**——BAD 块让每一轮都完整出现，且带明确的"我坏了"标记。

### ④ join「合并块读」
- **干什么**：把各块的 msg 按 `topic=blockNN` 拼回一个大对象 `{block00: [...], block01: [...]}`；
- **凑齐条件**：收齐 K 块（K=块数）才放行；另有超时兜底（2 倍通信超时），防极端情况卡死；
- **只有一块时**：没有 join，块装配直接进契约装配。

### ⑤ change「契约装配」（整条支路的心脏）
把合并结果拼成**北向契约报文**——这是和后端/下游约定好的固定格式：

```json
{
  "node_id": 66, "device_id": 49, "device_name": "123",
  "host_pc_ip": "192.168.0.179:1880",
  "ts": "2026-10-01T03:34:30.135Z",
  "value_count": 3,
  "values": [
    {"tag_id": 92, "tag_address": "100", "tag_name": "炉温", "raw_value": 5771,
     "register_type": "D", "eng_value": 57.7, "unit": "℃", "quality": "GOOD", "ts": "..."}
  ],
  "quality": "GOOD"
}
```

同时它还顺带算三样东西（都写在 msg 的附带字段上）：
- `comm`：本轮通信状态（有 BAD 块 → false，后面通信上报用）；
- `changeKey`：不含时间戳的数值指纹（变化触发用）；
- `pg_sql_i`：每个 PG 目标一条 INSERT 语句（如 `INSERT INTO public.plc_data_log (...) VALUES (...),(...)`）。

### ⑥ switch「有值才报」
- **规则**：`payload.value_count > 0` 才放行；
- **作用**：空轮（比如变化触发模式下值没变被 rbe 拦了的情况不会到这；这里是双保险）不打扰下游；
- **四路扇出**（放行后同一 msg 同时去四个方向）：MQTT 上报 / PG 写库 / 通信状态上报 / 数据出口。

## 第 3 章 上报与计数区（四路输出）

### 路线 1：mqtt out「MQTT 上报」
- 发到 `edgelink/gen/data/<节点ID>/<设备ID>`（topic 前缀可配，对拍期 edgelink/gen）；
- **这就是实时数据的出口**，后端监控大屏、第三方程序都从这里订阅；
- QoS 1。注意：broker 长期离线时实时数据会丢（MQTT 不带磁盘缓冲），历史数据靠 PG。

### 路线 2：PG 写库（多目标，可并行写多张表）
```
PG SQL·目标N (change)  →  写采集历史·目标N (postgresql)  →  PG成功计数·目标N
                              │(异常)
                    PG异常·目标N (catch)  →  PG失败计数·目标N
```
- **PG SQL·目标N**：把契约装配算好的 `pg_sql_0` 取到 `msg.topic`（postgresql 节点从 topic 读 SQL），并留 `pg_rows`（行数）供计数；
- **写采集历史**：执行 INSERT。库/模式/表/列子集在生成弹窗的"目标N"里各自独立配置；
- **成功/失败计数**：每轮把写成功的行数上报后端（监控页"PG 写入"列，每天 0:05 清零）；
- **两个调试观察口**（debug 节点）：「SQL调试·目标N」显示每轮实际 INSERT；「PG错误·目标N」显示 PG 报错原文。**写库失败先看这两个**（点节点上的按钮可临时关停，不影响采集）。

### 路线 3：http request「通信状态上报」
- 每轮把 `comm`（true/false）POST 到后端 `/monitor/device-comm-edge`；
- 监控页"PLC 在线/离线"就来自这里。**任一块 BAD = 整台离线**。

### 路线 4：link out「数据出口·设备名」
- **定制逻辑的正式接口**：新人要加"温度大于 80 就发通知"这类逻辑，**不要改本页**——新建自己的标签页，拖 link in 连这个出口，每轮都能拿到完整契约报文；
- 出口的 id 是固定的（确定性哈希），重新部署后你的 link in 连线不会断；
- 等价替代：直接订阅 MQTT topic（第 3 章路线 1）。

## 第 4 章 告警与异常区（红区）

### 告警链
```
MC Read 输出2(失败) ──→ 告警限速(delay, 30s/条) ──→ 告警时间戳(change) ──→ 告警报文(template) ──→ MQTT 告警
```
- **为什么限速**：PLC 断线时每秒都失败，不限速就是告警风暴。30 秒最多 1 条；
- **告警报文格式**：`{"alert_type":"PLC_OFFLINE","node_id":66,"device_id":49,...,"ts":"..."}`，发到 `edgelink/gen/alarm/plc_offline/<设备ID>`。

### 重连链
```
MC Read 输出2(失败) ──→ 重连限速(delay, 15s/次) ──→ 重连指令(change: topic=reinitialize) ──→ 回接首个 MC Read
```
- MC 连接是按设备共享的连接池，`reinitialize` 指令让连接重建一次即可；
- 15s 限速防"反复重连抖动"（PLC 闪断时不会每秒重建）。

### catch「支路异常」
- 兜底网：本页所有未捕获的异常（装配表达式写错、节点内部错误等）都会进这里 → 告警链；
- PG 支路有专属 catch（「PG异常·目标N」），不经过这个。

## 第 5 章 基础设施页（「基础设施」标签页）

| 节点 | 干什么 |
|---|---|
| 存量监控服务器（配置节点） | 后端地址 + 监控 Key。**Key 只录这一个地方**，两个功能节点共用 |
| 采集点健康度（site-health） | 定期上报本机运行指标（CPU/内存/流量）给存量监控页 |
| flows.json 上传 | 点节点按钮，把当前边缘画布快照传回后端留档（出问题时可下载对照） |
| MQTT broker（配置节点） | broker 地址/端口/凭证（凭证由部署自动下发或编辑器录入） |
| 采集库·目标N（配置节点） | PG 连接配置。注意：该包账号密码是明文字段 |
| 心跳（inject+http） | 每 30s 上报后端：维持监控页在线状态（90s 无心跳判离线），并携带 flow_version（部署回执——发布页"边缘在跑 vN"就靠它） |

**首次部署后必做**（画布下方注释里也写了）：① 录监控 Key ② MQTT 密码（生成时填了就跳过）③ PG 密码（同上）。

## 第 6 章 两种特殊模式

### 变化触发（设备表"触发方式"=变化触发）
```
契约装配 → rbe(有变化才报) → 有值才报 → 输出
```
- rbe 监视的是 `changeKey`（**不含时间戳的数值指纹**）——值没变就整轮静默，MQTT/PG/上报全不发；
- **为什么不能监视 payload**：payload 里有 ts，每轮必变，rbe 会永远放行——这是踩过的坑；
- 适用：变化稀疏的点位（开关量、状态量），省带宽省库。

### 亚秒采集（周期 <1000ms）
```
inject(一次性) → delay(节奏器, 比如 100ms) → MC Read… → 契约装配 ──→ 回接 delay
```
- inject 最小粒度是 1 秒，所以亚秒用"delay 自循环"：每轮结束后回接节奏器，隔 N 毫秒再来一轮；
- **自带背压**：下一轮 = 本轮耗时 + 延迟，PLC 再慢也不会堆请求；
- 代价：没有均匀时钟，周期是"采样间隔"而非"准点时刻"。

## 第 7 章 生命周期：配置如何变成画布

```
点位/设备配置（前端表单/Excel 导入）
   ↓ 【生成】后端 module_flowgen 编译
flows.json 版本（版本链，v1/v2/… 只前进不后退）
   ↓ 【部署】Admin API 推送到边缘 Node-RED（合并部署：只替换生成标签页，你的自定义页不动）
边缘运行
   ↓ 每 30s 心跳带回执（flow_version）
发布页横幅显示「边缘在跑 vN · 与最新版一致/不一致」
```

- **部署预览**：点部署会列出"将替换/将摘除/将新增/将保留"四张清单，生成区被手改过会红字警告；
- **回滚**：点历史版本的「回滚」，会以旧内容生成一个新版本（版本链不回头，可审计）；
- **画布快照**：每次部署自动把边缘完整画布（含你的自定义页面）存进后端，误删可下载恢复；
- **漂移检测**：编辑器里手改了生成页 → 横幅变红（录凭证、拖节点、连 link 线这些不算）。

## 第 8 章 新人 FAQ

**Q：数据没上来，第一步看哪里？**
A：看 MC Read 节点状态点（绿了在read/红了断开）→ 看「SQL调试」/「PG错误」调试侧栏 → 看发布页横幅是否漂移 → 看监控页 PLC 在线状态。

**Q：我能在生成页里改个表达式吗？**
A：不能。生成页是"编译产物"，下次部署会被覆盖。改配置去后台，重新生成部署。

**Q：为什么点位表里的"死区/计算点"不生效？**
A：本版（纯社区节点）不支持，前端入口已隐藏。配了会在生成时给 warning，不会静默生效。

**Q：PG 密码在哪里改？**
A：两条路：生成弹窗里填（随部署自动下发）；或编辑器里双击「采集库·目标N」录入（按节点 id 存活，重部署不丢）。

**Q：我自己加的页面会被部署删掉吗？**
A：不会。合并部署只动生成标签页（按确定性 id 认门），你的页面原样保留。唯一纪律：**你的页面别用 GEN_/EL_ 前缀命名**。

**Q：MQTT topic 前缀 edgelink/gen 是什么意思？**
A：与现网隔离的"频道"。切流前保持 edgelink/gen，切换正式通道时改 edgelink。别随手改——下游订阅的是完整 topic。

**Q：每天 0:05 PG 计数清零是 bug 吗？**
A：不是，是设计（看"今日"产量）。累计总量目前没留——需要的话提需求。

## 第 9 章 术语表

| 术语 | 含义 |
|---|---|
| 契约报文 | 边缘→后端/下游的统一数据格式（node_id/device_id/values[]/quality/ts） |
| 块读 | 一帧读多个连续寄存器（相对：一个点位一次读取） |
| 空洞容忍 | 地址间隙 ≤N 字时合并成一块，多读回来丢弃（跳址点位救星） |
| BAD/UNCERTAIN/GOOD | 质量码：读取失败 / 块成功但该点缺失 / 正常 |
| 变化触发 | 值不变不整轮上报（rbe 监视 changeKey） |
| 合并部署 | 部署只替换生成标签页，用户自建页面不动 |
| 漂移 | 边缘在跑的生成区与最新版本不一致（被手改/未部署） |
| 确定性 id | 节点 id = sha1(现场:角色:设备…)，重部署不变 → 凭证/连线/分组全部存活 |
| 生成器 | 后端 module_flowgen：把配置编译成 flows.json 的服务 |
