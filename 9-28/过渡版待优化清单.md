## A 组 — 正确性（会静默产出错数据）

### OPT-01 MC 多字类型无拼字逻辑 🔴

- **位置**：[generator_service.py:31](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L31)、[flow_builders.py:424](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L424)
- **现象**：`_WORDS_PER_TYPE` 给 `INT32/UINT32/FLOAT` 分 2 个字、`DOUBLE` 分 4 个字，但取值表达式是 `$lookup(payload, "D100")` —— **只取首字**，没有高低字拼接，也没有字节序处理。
- **证据**：`block_assemble_expr` 全链路只有 `$lookup`，无任何拼接；对比 [generator_service.py:438-444](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L438-L444)（Modbus 侧对跨寄存器类型**显式告警并跳过**）——同样一件事，两条支路处理完全不对称，MC 侧静默给错值。
- **建议**：三选一，需先确定库能力（见「M2 真机验证依赖项」V-2）：
  1. 库支持按类型解析 → 在块地址串上带类型/长度（如 `K4` 前缀）并让库直接返回解析值；
  2. 库不支持 → 沿用 Modbus 侧策略，生成期对该类型告警跳过；
  3. 折中 → 生成期告警 + 用 JSONata 按 `byte_order`/`word_order` 自行拼字。
- **验收**：构造含 `FLOAT`/`INT32` 各 1 点的设备，生成 → 真机读一个已知值（如 123.5），MQTT 报文 `eng_value` 与 PLC 监视值一致；`raw_value` 与拼字规则一致。
- **状态**：⬜
- **依赖**：V-2

### OPT-02 Modbus 侧 `data_type=BIT` 无位提取 🔴

- **位置**：[generator_service.py:438-444](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L438-L444)、[flow_builders.py:727-757](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L727-L757)
- **现象**：`_merge_blocks_modbus` 把 `BIT`/`BOOL` 当单字点位收进块（只要 `register_type` 相同），`modbus_block_assemble_expr` 直接 `payload[idx]` 取**整个寄存器**。配在 `HR` 上的 BIT 点位拿到的是字值，不是位值。
- **证据**：MC 侧有 `bit_offset` 处理（key 带 `.A`，见 [flow_builders.py:417-419](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L417-L419)），Modbus 侧完全没有对应逻辑，也没有告警。
- **建议**：两条路——(a) `register_type` 为线圈类（`CR`/`COIL`/`DISCRETE`）时按数组下标取值（现状正确，需补 `0/1` 语义）；(b) `register_type` 为字寄存器且 `data_type=BIT` 时，用 `bit_offset` 做位提取，或生成期告警跳过。
- **验收**：配置 1 个 `CR` 线圈点 + 1 个 `HR` 上的 BIT 点，真机比对 `raw_value` 与 PLC 实际位状态。
- **状态**：⬜

### OPT-03 FX 的 X/Y：块读地址串与取值 key 进制不一致 🔴

- **位置**：[generator_service.py:161](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L161)、[flow_builders.py:420-421](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L420-L421)、[flow_builders.py:73-74](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L73-L74)
- **现象**：块读地址用 `int(register_address)`（十进制）拼成 `X10,8`；取值 key 用 `int(str(addr), 8)` 转十六进制得到 `X8`。**同一台设备读 `X10`、找 `X8`**，`$lookup` 必然落空。
- **补充证据**：连接节点的 `octalInputOutput` 在本机现有装机版本（1.2.1）是**死参数**，而 [flow_builders.py:73](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L73) 的注释写着"连接级正确处理"——该注释在 1.2.1 上不成立。进制换算实际由地址串自身表示决定，因此三处（merge / lookup / 连接参数）必须统一。
- **建议**：先确定目标 MC 包版本（见 V-1）与其 X/Y 地址进制规则，然后让 `_merge_blocks` 的块地址串与 `tag_ref_expr` 的 key **走同一个换算函数**，并修正注释。
- **验收**：FX 系列 + `octalInputOutput=true`，读 `X0`~`X17` 全段，报文值与 PLC 监视值逐点一致；同时确认非 FX 系列未被误改。
- **状态**：⏸ 待真机
- **依赖**：V-1、V-3

### OPT-04 值缺失未判 BAD 🟠

- **位置**：[flow_builders.py:424](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L424)、[flow_builders.py:456](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L456)、[flow_builders.py:529](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L529)
- **现象**：好路 quality 恒 `"GOOD"`，但 `$lookup` 查不到 key 时返回 undefined → 该点位 `raw_value`/`eng_value` 在最终对象里**字段消失**（JSONata 会丢弃 undefined 值），而整条报文仍是 `GOOD`。下游看到的是"少了一个点位的好数据"。
- **影响面**：OPT-01/OPT-03 一旦成立，症状就是这个形态——**会掩盖前两条的现场表现**，所以要先修它，M2 排障才有信号。
- **建议**：取值改为带存在性判断，如 `($v := $lookup(payload,"D100"); $exists($v) ? $v : null)`，并在块内装配时按"有点位取不到值"降级该点 quality 为 `BAD`（块级 communication quality 可保持不变，避免把一次短读放大成整设备离线——具体语义待定，见备注）。
- **验收**：人为构造一个越界地址点位，生成的报文该点 `quality=BAD` 且 `raw_value=null`（不是字段消失），其余点位不受影响。
- **状态**：⬜
- **备注**：点位级 BAD 与设备级 `comm` 的关系需业务确认——是否让"个别点缺失"触发离线告警。

## B 组 — 规模与数据安全

### OPT-05 BIT 点位逐点一读，节点数爆炸 🟡

- **位置**：[generator_service.py:135-140](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L135-L140)、[_BLOCK_MAX_REGS / _NODE_COUNT_WARN](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L33-L35)
- **现象**：每个 BIT/BOOL 点位独立成块 = 独立 `MC Read` + 块内装配 + BAD 装配 = **3 节点/点**。注释里写了"连读 `M200.3,4`"，但代码没有实现批量。
- **量级**：一台设备 100 个 M 点 → 300+ 节点，加上字点位很快顶穿 [500 节点警戒线](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L35)（警戒提示本身也只是 warning，不阻断）。
- **建议**：把连续位号合并为一次块读（`M200.3,4` 或读整字后 JSONata 位提取），至少做到"同字节内的位合并"。
- **验收**：构造单设备 200 个 BIT 点 + 100 个字点位，生成节点总数与部署耗时记录在案；节点数较现状下降 ≥60%。
- **状态**：⬜
- **升级条件**：当目标现场单站点位数 > 150 时，本项升级为 🟠 投产前必修。

### OPT-06 PG 支路无断库兜底、无背压 🟠

- **位置**：[generator_service.py:306-320](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L306-L320)、[generator_service.py:293](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L293)
- **现象**：两条缺陷。
  1. **无 spool**：PG 写入是直连 `postgresql` 节点，断库期间数据直接丢失，只留一个 fail 计数。V12 有磁盘 spool 兜底（`edgelink-pg-store`）——**这是相对 V12 的能力倒退**。
  2. **无背压**：`final` 旁路同时触发 MQTT 与 PG，亚秒模式下 `final` 回接 `delay` 立刻进下一轮，不等 PG 写完；库变慢时消息在 postgresql 节点内堆积，**内存增长无上限**。
- **建议**：
  - 短期：PG 支路加"在途上限/丢弃计数"，并把队列积压暴露到 `pg-stat-edge`（现在只报 ok/fail 条数，看不到积压）；
  - 中期：评估用社区节点实现文件 spool（若无法实现，须在文档与售前明确"断库即丢数据"）。
- **验收**：断库 5 分钟后恢复，记录丢失条数与内存峰值；确认进程未 OOM、恢复后自动续写。
- **状态**：⬜
- **备注**：无论修不修，**都必须在交付文档里写明这条与 V12 的差距**。

### OPT-15 PLC 离线时固定周期刷 BAD/null 行（无降采样）🟠

- **位置**：[generator_service.py:312](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L312)（`trigger_change`）、[generator_service.py:368](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L368)（`downstream = rbe_id if trigger_change else switch_id`）、[flow_builders.py:550](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L550)（`pg_sql_expr`）
- **现象**：`trigger_kind` 默认固定周期（`(trigger_kind or 1) == 2` 才变化触发）。固定周期支路**没有 rbe**——`downstream` 直接走 `switch_id`，每轮扫描读失败都进 `bad_ids` → BAD 装配 → `pg_sql` 落库 **N 条 `quality='BAD'` / 值缺失行**。设备离线一小时，1s 周期单设备 4 点就是 ~14.4k 条脏行；多设备、多点、维护窗口级离线会显著放大时序库体积，并污染按 `quality` 统计的可用性指标。
- **为什么不能靠加 rbe 修**：`make_rbe` 监视 `changeKey`（不含 ts 的数值指纹），本质是"同值去重"；而离线 BAD 行是**时序列**（每轮都该记录失败时刻，只是不需要逐秒记录）——去重解决不了，正确手段是**降采样**。
- **建议**：
  - 短期：固定周期支路在 PLC 连续离线时降采样——连续失败后只在首次、以及此后每 N 分钟记一行 BAD（离线状态已有 `/device-comm-edge` 直报 + 监控页 90s 判定，PG 里无需逐秒刷）；
  - 或：把 BAD 装配的 PG 写入与 MQTT 解耦，PG 只落 `GOOD`/变化行，离线由告警 + `/device-comm-edge` 表达（与 OPT-11 告警语义联动）。
- **验收**：人为停一台 PLC 10 分钟，`plc_data_log` 新增行数显著少于 `scan_interval` 应产生的量；MQTT 离线告警与监控页离线判定不受影响。
- **状态**：⬜
- **关联**：OPT-06（同属 PG 支路：一个"断库丢数"、一个"离线刷脏"）、OPT-11（BAD 语义与告警分离）

## C 组 — 运维闭环

### OPT-07 kill switch 远程停采 🟠

- **位置**：[monitor_controller.py:141-150](../ruoyi-fastapi-backend/module_plc/controller/monitor_controller.py#L141-L150)（后端下发）、[flow_builders.py:776-853](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L776-L853)（生成流判定链）
- **核实（2026-09-30 读码）**：**已按本条「建议」实现完毕，原「现象」已过时**。链路四段齐备：
  1. **后端**：`/heartbeat-edge` 返回 `data.disabled`（查 `EdgeBootstrapKey.enabled`），与 V12 `/heartbeat` 同语义；
  2. **心跳支路**：`make_heartbeat_branch` —— inject 30s → 心跳（带 `flow_version`）→ 写 global `edgelink_disabled` → `rbe` 仅状态变化时放行 → switch 分流「停采指令」(`topic=disconnect`) / 「恢复指令」(`topic=connect`) → link out 分发到各设备支路；
  3. **落点**：各设备支路 `link in`「停采控制入口」回接该设备首个 MC Read（[generator_service.py:404](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L404)）；
  4. **数据闸门**：`make_switch_nonempty` 规则二 = `$globalContext("edgelink_disabled") != true`（[flow_builders.py:259](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L259)），MQTT / PG / 通信状态上报全在闸门之后；告警与重连支路另有 `make_disable_gate`。即停采期间**不出数、不告警、不上报通信状态**。
- **原现象（已过时）**：`/heartbeat-edge` 曾只返回 `{'node_id': node_id}`；现返回 `{'node_id', 'disabled'}`。
- **验收已覆盖**：翻转经 `rbe` 去重，只在状态变化时下发一次；恢复无需重启 Node-RED。
- **待真机验证（残余）**：`topic=disconnect/connect` 是否被现场装的社区 MC 节点接受（依赖 V-1 包名与版本）。**但闸门与节点版本无关**——即使节点忽略该控制消息，第 4 点的数据/告警闸门仍生效，验收要求的"MQTT 无数据、不刷告警"照样成立；受影响仅限 PLC 侧 TCP 是否真的断开（少一层减负）。
- **已知小窗口**：心跳 inject 为 `once:true, onceDelay:5`，Node-RED 重启后 global 丢失（默认内存态 contextStorage），重启到首次心跳之间约 5s 闸门是开的。在意可把 `onceDelay` 调到 0/1；**不建议**把闸门改成"必须显式 false 才放行"——那会在后端短暂不可达时静默停采，代价更大。
- **状态**：🧪 已修改待真机验证（除 disconnect 控制项外，其余读码即可确认）

### OPT-08 无部署回执，边缘实际版本不可知 🟠

- **位置**：[monitor_controller.py:104-129](../ruoyi-fastapi-backend/module_plc/controller/monitor_controller.py#L104-L129)、[generator_service.py:781-797](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L781-L797)
- **现象**：整条链是**开环**的。后端记录"生成了第 N 版（`plc_flow_release`）"，但不知道边缘实际部署了哪一版、部署是否成功——`/heartbeat-edge` 不接收 `config_version`。
- **影响**：无法回答"现场那台机器跑的到底是不是我刚发的版本"，这是后续批量运维与故障定责的前提。
- **建议**：生成产物内嵌 `release_version` + `sha256`（写进基础设施 tab 的注释节点与一个 readonly 变量），心跳上报时带上；后端 `nodered_node` 增加记录并与最新 release 比对，不一致即在监控中心标"版本不符"。
- **验收**：生成 v3 但边缘仍跑 v2 时，监控中心明确显示版本不符；部署 v3 后一格内自愈。
- **核实（2026-09-30 读码）**：**已按「建议」实现，原「现象」已过时**——① `/heartbeat-edge` 接收 `flow_version`（[monitor_controller.py:109](../ruoyi-fastapi-backend/module_plc/controller/monitor_controller.py#L109)）并写入 `nodered_node.config_version`（[L134-139](../ruoyi-fastapi-backend/module_plc/controller/monitor_controller.py#L134-L139)）；② 产物内嵌占位 `__FLOWVER__`，发布时替换为版本号（[generator_service.py:882](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L882)），心跳 URL 携带（[flow_builders.py:791](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L791)）；③ 监控侧有比对与提示：发布页「边缘已应用版本」与最新快照对比，落后即第 4 卡转红。
- **状态**：🧪 已修改待真机验证（待真机确认：生成 v3 而边缘仍跑 v2 时发布页确实转红）

### OPT-09 亚秒自循环在 `busy` 未复位时会整条停摆 🟠

- **位置**：[generator_service.py:245-247, 293](../ruoyi-fastapi-backend/module_flowgen/service/generator_service.py#L245-L247)
- **现象**：亚秒模式（`scan_interval_ms < 1000`）的循环是 `inject(once) → delay → read → … → final → delay`，**下一轮完全由 `final` 触发**。而社区 MC Read 有 `if (node.busy) return;` 的丢弃闸——若超时路径未复位 `busy`，`final` 永不触发，**该设备永久停摆且无任何告警**（数据管道静默）。≥1s 模式用 inject 周期触发，不受影响。
- **建议**：先真机验证超时后 `busy` 是否复位（见 V-4）；若不复位，加"轮次看门狗"——一个独立的低频 inject 兜底触发 `delay`，或亚秒模式改用"inject 1s 周期 + delay 内部再分频"的两级结构。
- **验收**：真机拔网线 30s 后恢复，确认亚秒模式设备自动续采；或确认看门狗在停摆 N 秒后强制重启轮次。
- **状态**：⏸ 待真机
- **依赖**：V-4

### OPT-16 三层离线信号独立，缺统一「节点在线」交叉校验 🟡

- **位置**：[flow_builders.py:790](../ruoyi-fastapi-backend/module_flowgen/service/flow_builders.py#L790)（`make_heartbeat_branch` 心跳）、[monitor_controller.py:175](../ruoyi-fastapi-backend/module_plc/controller/monitor_controller.py#L175)（`/device-comm-edge` 设备态）、点位 `quality`（报文内）。三层判定互不校验。
- **现象**：节点在线只看 `last_heartbeat`（90s）；数据采集走 MQTT/PG 直连、与心跳**解耦**。这是**刻意设计**（好处：监控后端故障不影响采集主链路）。代价是：心跳链路一旦静默失效，没有其它信号交叉验证"节点到底还活着"——本会话真机即中招：`/heartbeat-edge` 漏 import `select` 抛 `NameError`，`last_heartbeat` 从不落库，节点离线了一整天，而采集（MQTT/PG）一直正常出数，直到人工核对才发现。
- **为什么不是"统一成一个心跳"**：采集与心跳解耦有真实价值（不因监控故障停采、不因单点失败串扰），V12 与生成版都刻意保留。问题不在"要不要分开"，而在"分开后缺一条互相兜底的交叉校验"。
- **建议**（二选一或组合）：
  1. **交叉校验**：后端判定节点离线时，反查近 90s 内是否有该节点的 `pg-stat-edge` / `device-comm-edge` / MQTT 数据到达；若有，把"离线"降级为"心跳异常（采集仍在线）"告警，而非直接标离线；
  2. **心跳自证**：心跳载荷带上最近一次数据管道成功时间（`last_data_ts`），后端据此区分"真离线"与"心跳上报故障"。
- **验收**：人为制造心跳 500（但采集正常），监控页不再误标"离线"，而是显示"心跳异常"/"采集在线但心跳缺失"；真实断连时仍正确标离线。
- **状态**：⬜
- **关联**：OPT-08（部署回执同样依赖心跳，心跳失效时一并失真）、OPT-11（告警语义区分）
