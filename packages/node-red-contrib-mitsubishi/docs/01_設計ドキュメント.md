## 1. 設計理念（Design Philosophy）

### 1.1 核心原則：プロトコル層とアプリケーション層の分離

```
┌──────────────────────────────────────────────┐
│  Node-RED ノード層 (mitsubishi-read/write)   │
│  ・メッセージルーティング                      │
│  ・タグ解決（msg.tags → 静的設定 → フォールバック）│
│  ・出力組立（rawValue / engValue / quality）  │
│  ・ライフサイクル管理（close / _closed ガード）│
├──────────────────────────────────────────────┤
│  接続プール層 (getConnection / release)       │
│  ・TCP/UDP 透過抽象                           │
│  ・指数バックオフ + キュー制御（上限 50）       │
│  ・参照カウント + アイドルクリーンアップ         │
│  ・接続キー粒度: host:port:frame:net:station:proto│
├──────────────────────────────────────────────┤
│  プロトコル層 (mc-protocol.js)                │
│  ・3E/4E フレーム構築・解析（純粋関数）         │
│  ・タグデコード（16/32/64 ビット全対応）       │
│  ・グルーピング（読取: 20 gap 許容 / 書込: 厳密隣接）│
│  ・工程値変換（slope/offset + roundEng 精度保証）│
│  ・ASCII 透過シム（STX/ETX/チェックサム）       │
├──────────────────────────────────────────────┤
│  トランスポート層 (mc-udp.js / net.Socket)    │
│  ・TCP: ストリーム分割・再組立                  │
│  ・UDP: セッション管理 / ICMP エラー隔離        │
└──────────────────────────────────────────────┘
```

### 1.2 設計判断の根拠

| 判断 | 根拠 | トレードオフ |
|------|------|-------------|
| **ゼロ依存** | 本番環境でのサプライチェーンリスク排除。MC プロトコルは仕様が安定しており、外部ライブラリの更新に追従する必要がない | プロトコル更新は自前実装が必要 |
| **読取・書込プール分離** | 書込は散発的。同一ソケット共有では書込が読取周期をブロックする（MC は要求-応答直列） | 接続数が最大 2 倍（1 PLC あたり 2 ソケット） |
| **接続キーに frame/network/station を含める** | 同一 PLC に 3E と 4E 両方で接続する構成でパラメータが競合しない | 接続数が増加しうる（実用上稀） |
| **書込グループは厳密隣接のみ** | ギャップを埋めるゼロ書込は PLC の未設定データを破壊する。読取側は 20 ワードのギャップ許容（読過剰は無害） | 書込フレーム数が増加しうる |
| **roundEng は大値スキップ**（`|v|≥9e5`） | `v*1e10` が 2^53 に接近すると丸め自体が誤差を導入する。大値は整数であり浮動小数点テールを持たない | 極端な大値 + 小数の組み合わせでテールが残留しうる（実用上存在しない） |

## 2. 安全機構（Safety Mechanisms）

### 2.1 データ完全性

```
[PLC] ──読み取り──→ [フレーム検証] ──→ [デコード] ──→ [品質マーキング] ──→ [出力]
                        │                │              │
                        ├ サブヘッダ検証  ├ ワード欠落検出 ├ quality=0 (GOOD)
                        │  (3E:0xD0,    │  (多ワード型)  ├ quality=2 (BAD/欠損)
                        │   4E:0xD4)     ├ アドレス範囲外  └ エラーコードテキスト
                        ├ 最小フレーム長  └ 型変換ガード
                        ├ データ長範囲
                        ├ シリアル番号照合(4E)
                        └ エンドコード≠0 → エラーテキスト
```

- **`rawValue`**: デコード済み完全値（FLOAT32 は 2 ワード組立後、DOUBLE は 4 ワード組立後）
- **`rawWord`**: 生の先頭ワード（監査用）
- **`engValue`**: `roundEng(rawValue * slope + offset)` — 10 桁小数精度保証
- **`quality`**: ポイント単位で 0=GOOD / 2=BAD、下流はこれでデータ信頼性を判定可能

### 2.2 接続ライフサイクル

```
              ┌─ 成功 → inUse=true → リクエスト実行 → release
              │
getConnection─┼─ 接続中(connecting) → キュー登録（上限 50、超過は明示的 reject）
              │
              ├─ バックオフ中 → 残り時間付きで即時 reject（再試行嵐防止）
              │
              └─ 新規接続 → net.connect() → setKeepAlive(true, 30000)
                     │
                     ├─ 成功 → コールバック → リクエスト実行
                     └─ 失敗 → 指数バックオフ (base=retryInterval, max=10s)
```

### 2.3 書込安全機構

```
書込タグ
  │
  ├─ ビットデバイス (M/X/Y/L/B) → ネイティブビット書込 (0x1401/0x0001)
  │     └─ ギャップ検出: 隣接ビットのみ同一フレーム、飛びビットは分割
  │
  ├─ ワードデバイス BOOL (D100.3) → RMW（Read-Modify-Write）
  │     └─ 現在値読み取り → ビット変更 → 書き戻し（競合: JS 単一スレッドにより直列化）
  │
  └─ ワードデバイス非 BOOL → バッチワード書込 (0x1401/0x0000)
        └─ `groupTagsContiguous`: `t.addr === clMax + 1` 厳密隣接チェック
              ├─ 隣接 → 同一フレーム（最大 960 ワード）
              └─ 非隣接 → 新規フレーム（絶対に隙間をゼロで埋めない）
```

## 3. プロトコル準拠（Protocol Compliance）

### 3.1 サポート対象

| 項目 | 対応 |
|------|------|
| フレーム形式 | 3E (QnA 互換), 4E (SLMP) |
| トランスポート | TCP (ストリーム分割再組立), UDP (セッション管理 + ICMP 隔離) |
| 通信モード | バイナリ (全フレーム), ASCII (STX/ETX/チェックサム, 3E/4E 両対応) |
| PLC シリーズ | Q, L, iQ-R, iQ-F, FX5U (X/Y アドレス基数自動判定) |
| データ型 | INT16, UINT16, INT32, UINT32, FLOAT32, DOUBLE, BOOL |
| ソフトデバイス | D, W, R, X, Y, M, L, B |
| 最大読取点数 | 1 リクエストあたり 960 ワード（プロトコル上限）、ノード内自動分割で無制限 |
| 最大書込点数 | 1 リクエストあたり 960 ワード（ギャップ検出により隣接ブロックごとに自動分割） |

### 3.2 3E フレーム検証状態

**リクエスト・レスポンスともに実機 (Q シリーズ) + pymcprotocol 対照で逐バイト検証済。エラーなし。**

**pymcprotocol `type4e.py` および SH-080008 (三菱 SLMP リファレンスマニュアル) と逐バイト対照済。**

| シリアル番号 | 2-3 | 2 | LE | pymcprotocol 対照 |

## 5. 既知の制限と誠実な開示

### 5.1 未検証項目

1. **4E フレーム実機通信**: iQ-R/FX5U での 4E フレーム通信は未実施。フレーム構造は SLMP 仕様書とリファレンス実装で検証済だが、実機確認が推奨される。
2. **接続プール競合ウィンドウ**: `_closed` フラグと非同期コールバックの競合は論理検証済（JS 単一スレッドモデルにより同一イベントループ内で競合しない）だが、故障注入テストは未実施。

### 5.2 設計上の制約

1. **単一 PLC への同時リクエスト数 = 1**: MC プロトコルは要求-応答直列のため、同一接続での並列リクエスト不可。`IN_FLIGHT` ゲートで超過リクエストは明示的に拒否。
2. **Node.js ≥ 14.0.0**: `Buffer.alloc` / `unref()` 等の API に依存。
3. **開発者単一**: 現在のメンテナは 1 名（EdgeLink Team）。バス係数リスクは GitHub Issues で軽減。

### 5.3 移行時の注意点

- mcprotocol ノードとの共存は可能（別ノードタイプのため競合しない）
- 設定形式が異なるため、既存 flow の移行にはタグの再設定が必要（CSV インポートで一括移行可）
- TCP と UDP で同一のタグ設定を使用可能（プロトコル透過）
