# 我把三菱 MC 节点重写到了 v1.5.1：先承认上一版的三个致命 Bug，再谈超越

> 系列前文：《我在 Node-RED 里重造了三菱 PLC 采集节点：一个工业工程师对 mcprotocol 的 7 个不满》
> 包地址：`npm install node-red-contrib-mitsubishi`（当前版本 v1.5.1）
> GitHub：https://github.com/Qq225083/node-red-contrib-mitsubishi

## 写在前面：这篇不是宣传稿，是一份 bug 自白书

上一篇文章发出去后，这个包被不少人装去用了。但我得先坦白一件事：**v1.4.3（就是你们从 npm 装到的那个版本）带着三个致命 bug**，其中两个还是"静默错数据"——最危险的那种，它不报错，数据照常进库，只是值是错的。

v1.5.1 就是修完这些 bug 再加写入能力的版本。这篇文章按顺序讲：旧版哪里错了 → 我怎么证明新版是对的 → v1.5.1 到底能干什么 → 实测数据 → 和 mcprotocol 的最新对比 → 还没做的事。

## 一、旧版的三个致命 Bug（如果你在用人肉绕过它们，对不住）

### Bug 1：4E 帧字节布局整体错位——iQ-R/FX5U 真机必挂

SLMP 4E 帧的规范布局是：

```
54 00 | 序列号(2) | 固定值 00 00(2) | 网络号 | PC号 FF | IO号 FF 03 | 站号 | 数据长(2) | 定时器 | 指令 | 子指令 | ...
```

旧版把序列号塞到了监视定时器**后面**，还弄丢了 2 字节固定值，数据长写成 14（应为 12）。三套证据交叉确认它错了：pymcprotocol 源码、本机另一份 mcprotocol 实现、三菱官方手册 SH-080008。后果：4E 模式下任何真实 iQ-R/FX5U 要么报帧格式错误，要么访问路由解析错位无响应。讽刺的是旧版的单元测试**按同样的错误布局断言**——测试把错误锁死了。

### Bug 2：32/64 位点位数据断线——FLOAT32 读出来全是错的

这是我最不愿意承认的一个，因为上一篇文章里我拿 FLOAT32 自动解码当过卖点。

节点内部其实把 FLOAT32/INT32/DOUBLE 解码得**完全正确**，但解码结果被写进了一个叫 `convertedValue` 的字段，而输出的 `rawValue` 永远是**第一个 16 位字**。下游（data-processor）只消费 `rawValue`——全链路 17 个函数里 `convertedValue` 零引用。

翻译成人话：**FLOAT32=23.5 存在 D200/D201，你收到的是 D200 那一个字的整数值。** INT16/UINT16 点位不受影响（单字即全值），所以大部分人没察觉。第一个配 FLOAT 点位的用户就会踩中。

### Bug 3：批量写"间隙填 0"——会清空 PLC 里你没配置的地址

v1.5.0 开发写节点时我发现了这个设计陷阱（幸好是在真机验证前）：MC 批量写是连续地址写入，如果一组点位是 D100 和 D110，那么 D101~D109 必须也写点什么——填什么？第一反应是填 0。**这就意味着写 2 个点会顺手清空 9 个你没碰过的寄存器**——如果那是 PLC 程序在用的配方值或设定值，一次写入就是一次生产事故。

位写也一样：写 M100 和 M105，中间 M101~M104 会被显式写成 0（我用脚本实证过帧内容）。

## 二、怎么证明"这次修对了"——把测试从"锁死错误"改成"对拍规范"

协议节点的测试有个通病：开发照着理解写实现，再照着实现写测试，测试通过 ≠ 实现正确，只等于"实现==理解"。旧版的 4E 测试就是这么废掉的。

v1.5.1 的测试换了个做法——**golden buffer 对拍**：用第三方权威实现（pymcprotocol）和规范手册生成"标准答案帧"，逐字节比对：

```js
// 4E 批量读帧（25 字节）：D100, 2 字, 站号 0, 序列号 0x1234
var expected = Buffer.from([
  0x54, 0x00,             // 副标题
  0x34, 0x12,             // 序列号 LE（副标题内，偏移 2-3）
  0x00, 0x00,             // 固定值（偏移 4-5）
  0x00, 0xFF, 0xFF, 0x03, 0x00,  // 路由
  0x0C, 0x00,             // 数据长 = 12
  0x10, 0x00,             // 监视定时器
  0x01, 0x04, 0x00, 0x00, // 指令 0x0401 + 子指令
  0x64, 0x00, 0x00, 0xA8, // 地址 100 + 软元件代码 D
  0x02, 0x00              // 点数 2
]);
assert.deepStrictEqual(mc.build4EFrame(100, 2, 0, 'D', 0, 0x1234), expected);
```

现在套件一共 **97 个测试**，覆盖：

- 3E/4E 读写帧 golden buffer（含 dataLen 逐字段断言）
- 编解码全组合：INT16/32、UINT、FLOAT32/64、BOOL × byteOrder/wordOrder/bitOffset
- **编码↔解码往返对称**（写一个值再读回来必须相等——写节点正确性的最直接证明）
- 分组逻辑：连续/间隙/960 字封顶/混型/位元件
- UDP 端到端（dgram 模拟 PLC：3E/4E/丢包重试）
- 请求级超时（mock PLC 装死，验证重连链不炸异常）
- **10,000 点位压测**（帧数、耗时、内存有界）

## 三、v1.5.1 能干什么

### 读取（v1.4.4 起）

- 3E/4E 帧（规范布局，对拍验证）、TCP/**UDP** 双传输
- 7 种数据类型 × byteOrder/wordOrder/bitOffset 全组合，slope/offset 变换，计算点位（add/sub/mul/div）
- X/Y 进制按系列区分（FX=8 进制，Q/L/iQ-R=16 进制——旧版把 Q 当 8 进制是错的）
- **960 字 span 感知聚类**：1 万连续点位只发 11 帧（旧版 200+ 帧）

### 写入（v1.5.1 新增）

三条写入路径，按点位类型自动分流：

| 点位类型 | 路径 | 为什么 |
|---|---|---|
| 字（D/W/R，INT16~DOUBLE） | 批量写 0x1401 | 一帧写完 |
| 位设备（M/X/Y/L/B） | **原生位写 0x1401/0x0001** | 单往返，无竞态 |
| 字内位（D100.3） | RMW（读-改-写） | 唯一必须 RMW 的场景 |

**写安全设计（这个节点和别家最大的区别）**：写分组**严格连续**——两个目标地址之间有间隙就拆成两帧，**绝不向中间地址写 0**。宁可多发几帧，也不碰不该碰的寄存器。

### 工程韧性（读写共用）

- 连接池（读/写独立）+ per-PLC 轮次闸：慢 PLC 场景新轮次直接丢弃，不积压过期数据
- `_closed` 全路径守卫：重部署落在任何回调窗口都不会楔死连接
- 请求级超时：write 后 timeout 内必须拿到完整帧（防慢滴漏响应绕过 socket 空闲超时）
- 错误全部 `node.error(text, msg)`：编辑器里挂 catch 节点就能捕获

## 四、实测数据（不吹，全是可以复现的）

万点压测（dgram 模拟 PLC，10,000 连续 INT16）：

| 指标 | 数值 |
|---|---|
| 帧数/轮 | **11 帧**（960 字聚类） |
| 单轮耗时（本机 loopback） | ~190ms（含 1 万个点位对象装配） |
| 内存（3 轮×10k） | +11MB，GC 可回收，有界 |

单帧解码成本实测：0.11μs/点；10k 点位 payload 的 JSON 序列化：6ms。**瓶颈从来不在 CPU，在帧数和 PLC 响应时间。**

直接给结论性的容量建议：

| 场景 | 可行性 |
|---|---|
| 单 PLC 100ms 周期 | ≤1000 点（≤2 帧） |
| 单 PLC 10k 点 | 周期 ≥1000ms（单轮 ~200ms，占 20%） |
| 硬要 100ms×10k | 多实例分摊（PLC 以太网口支持 8~16 并发连接，EdgeLink 多实例模型原生支持） |

## 五、和 mcprotocol 的最新对比（v1.5.1 版）

| 维度 | 本节点 v1.5.1 | mcprotocol(mcprotocol-ind) |
|---|---|---|
| 点位数量 | N 个/节点 | 1 个/节点 |
| 帧 | 3E/4E（规范对拍） | 1E/3E/4E |
| 传输 | TCP + UDP | TCP + UDP |
| 读取类型 | 7 种 × 字节序/字序/位偏移 | 基础类型 + CHAR |
| 写入 | 字批量 + **位原生写** + RMW | 字批量 + 位原生写 |
| 写安全 | **严格连续，绝不向间隙写 0** | 批量写连续覆盖 |
| 软元件 | D/W/X/Y/M/L/B/R（8 种） | 全家族（T/C/SM/SD/SB/SW…） |
| ASCII 模式 | ❌ | ✅ |
| 测试 | **97 项（对拍/压测/e2e）** | 无 |
| 内存安全 | 有界队列+轮次闸+close 清理 | 有监听器/定时器泄漏（前文分析过） |
| 维护 | 活跃（2026-07） | 停更/低频 |

**一句话**：要 1E/ASCII/老 A 系列/全软元件家族 → mcprotocol；要读写高频采集、万点规模、测试护栏和写安全 → 本节点。

## 六、还没做的事（继续诚实）

- 软元件只有 8 种，定时器/计数器/特殊继电器（T/C/SM/SD）没覆盖（排期中，每种就是设备码表加一行）
- ASCII 模式没有（部分老现场只开 ASCII 口，按需补）
- STRING 读写没有
- 编辑器全中文，国际化欠着（如果 issue 里要的人多就补）

## 七、30 秒上手

```bash
cd ~/.node-red
npm install node-red-contrib-mitsubishi
# 重启 Node-RED，左侧面板出现「三菱 PLC」分类
```

读取：拖入 `PLC 连接配置`（选 TCP/UDP、帧格式、PLC 系列）→ 拖入 `MC 读取` → 表格填点位（支持 CSV 导入）→ inject 触发。

写入：拖入 `MC 写入`，同样关联配置，`msg.payload.tags` 下发：

```js
msg.payload = {
  tags: [
    { id: 'setpoint', regType: 'D', addr: 200, dataType: 'FLOAT32', value: 23.5 },
    { id: 'run',      regType: 'M', addr: 100, dataType: 'BOOL',   value: 1 }
  ]
};
return msg;
```

模拟模式（无 PLC 调试）：`settings.js` 加 `mcSimulationMode: true`。

## 结尾

这个版本的教训比功能值钱：**协议节点"能跑通"和"是对的"之间，隔着一套对拍测试；写入功能"能写"和"敢写"之间，隔着一条"绝不碰未配置地址"的纪律。** 如果你在用一个从没做过 golden buffer 对拍的协议包——不管是不是我的——建议先拿真机抓一帧对一下再说。
