- 配置驱动生成：后端设备/点位/采集点 → `module_flowgen` → flows.json → Admin API 合并部署。
- 确定性节点 id：`sha1(site:role:device...)[:16]`，用于 credential 存活、合并部署、漂移检测、link out 连线存活。
- 版本链/发布/回滚/画布快照/漂移检测/部署预览均已落地。
- 数据面：MC/Modbus → 块读 → 块内装配 → join → 契约装配 → MQTT / PG / link out。
- 基础设施：site-health-server、site-health、flows-upload、MQTT broker、PG 配置、心跳（30s）。
- PG 多目标、列子集、模式/表可配；字符串单引号转义；bool→1/0；必填列强制包含。
- 亚秒采集：inject 最低 1s，<1s 用 `inject(once) + delay` 自循环。
- 变化触发：rbe 监视 `changeKey`（不含 ts）。
- 监控：心跳 30s/90s 离线、离线区间、异常履历 7 天、Teams 断线通知。

- 黄金快照（130 节点）作为回归基线；节点契约 lint；冒烟测试。

## 3. P0 问题清单（带证据与最小修复）

### P0-1 位设备地址与输出键契约（最高优先级）

**现象**

- 位设备 `M/L/F/V/X/Y/B` 生成 `M200.3,4` 这类地址；MC 包实际输出键是 `M200`、`M201`、`M202`、`M203`。
- 生成器 `tag_ref_expr` 对 `BIT/BOOL` 无条件拼 `.{bit:X}`（`flow_builders.py:483-499`），于是 `$lookup(payload, "M200.3")` 找不到 key → 块内装配把该点标成 `UNCERTAIN`、raw/eng=null（`flow_builders.py:511-542`）。

**证据**

- `flow_builders.py:493-495`：
  ```python
  if data_type in ('BIT', 'BOOL'):
      bit = int(tag.get('bit_offset') or 0)
      key = f'{reg_type}{addr}.{bit:X}'
  ```
- `read.js:168-198`：`msg.dataType == "BIT" && msg.deviceCodeType != "BIT"` 才拼 `.bit`；否则走 else，key 是 `M200`，`iWD += dataTypeByteLength/2`（位设备为 1），即 `M200..M203`。
- `mcprotocol.js:3229-3236`：BIT 分支 `remainder = offset % 16`，`requestOffset = offset - remainder`，`bitNative = isBitDevice()`。
- `mcprotocol.js:3252`：`wordLength = ceil((remainder + arrayLength) / 16)`。
- `mcprotocol.js:1677`：`result.deviceNo = theItem.offset`（=200），所以 read.js 从 200 开始编号。
- `generator_service.py:183-227`：BIT 连读按 `register_address*16 + bit_offset` 排序，并生成 `M{start_addr}.{start_bit:X}`。

**根因**

生成器把“字设备的字内位”语义套到了“位设备”上：

- 对字设备 `D/W/R`：`register_address` 是字地址，`bit_offset` 是 0–15 的位号；key 应是 `D100.3`。
- 对位设备 `M/L/F/V/X/Y/B`：地址本身就是位号；不存在“字内位”。key 应是 `M200`（或按偏移 `M200+n`），**不能带 `.bit`**。

当前 `_merge_blocks` 用 `register_address*16 + bit_offset` 排序，导致：
- 单个 `M200.3` 会被当成“字 200 的 bit 3”，但地址串 `M200.3` 被包解析为 offset=200、bitNo 被忽略，实际读 `M200`；
- 多个 bit 合并成 `M200.3,4` 时，包读 `M200..M203`，但生成器以为读的是 `M200.3..M200.6`，语义整体错位。

**正确契约（建议写进生成器文档）**

| 设备类别 | 地址模型 | 生成读地址 | 输出 key |
|---|---|---|---|
| 位设备 M/L/F/V | 位号（十进制） | `M{start},{count}`（单点可省略 `,count`） | `M{bit}` |
| 位设备 X/Y/B | 位号（X/Y 按机型：FX 八进制 / 非 FX 十六进制；B 十六进制） | `X{按包要求的进制}` / `X{start},{count}` | 与读地址一致的进制大写 |
| 字设备 D/W/R，非 BIT | 字地址 | `D{start},{count}` | `D{addr}` |
| 字设备 D/W/R，BIT/BOOL | 字地址 + 位号 0–15 | `D{addr}.{bit:X}`（连读 `D{addr}.{bit:X},{count}`） | `D{addr}.{bit:X}` |

**位设备 `bit_offset` 语义必须先定死**（三选一，推荐第 3 种）：

1. `register_address` 是位号，`bit_offset` 必须为 0/空；为兼容旧数据，非 0 时报错要求修正。
2. `register_address` 是字基址，`bit_offset` 是字内位号——这只适用于字设备，不适用于 M。
3. `register_address` 是基位号，`bit_offset` 是偏移量；全局位号 = `addr + bit_offset`。这与前端“位偏移”标签最接近，也最容易迁移。

**最小修复**

1. 在 `_merge_blocks` 里按 `register_type` 分流：位设备走“位号连续”分支，字设备走“字+位”分支；位设备地址串不带 `.bit`。
2. `tag_ref_expr` 增加 `is_bit_device` 判断：位设备 key 用 `{reg_type}{global_bit}`，字设备 BIT 才用 `.bit`。
3. 把 `_validate_inputs` 的位偏移校验改成“按设备类别校验”：位设备允许 0 或偏移；字设备 0–15。
4. 黄金/冒烟断言从“字符串相等”升级为“地址 + 预期 key 集合”双断言；当前 `test_flowgen_smoke.py` 只断言 `M200.3` / `['M200.3,2','M200.9']`，属于**假绿**。

**验收用例（必须做）**

- 单点：`M200`（bit_offset=0）→ 地址 `M200`，key `M200`。
- 连续：`M200`、`M201`、`M202` → 地址 `M200,3`，keys `M200/M201/M202`。
- 偏移：`M200` + bit_offset=3 → 若采用第 3 种语义，地址 `M203`，key `M203`。
- 字设备：`D100` + bit_offset=3 → 地址 `D100.3`，key `D100.3`。
- 字设备连续位：`D100.3,4` → keys `D100.3..D100.6`。
- 位设备连读：`M200..M203` → 地址 `M200,4`，keys `M200..M203`（**不是** `M200.0..M200.3`）。

### P0-2 没有自动重连

**现象**

- 断线后 MC Read 只报 `Not connected!`，不会自己恢复；Net 上的“1s 自动重连”不成立。

**证据**

- `connection_pool.js:45-46`：
  ```js
  options.autoConnect =
    options.autoConnect == "undefined" ? true : options.autoConnect;
  ```
  未传 `autoConnect` 时，`options.autoConnect` 是 `undefined`，与字符串 `"undefined"` 比较为 false，结果仍是 `undefined`（falsy）。
- `connection_pool.js:75-82`：`read()` 未连接直接 `throw new Error("Not connected!")`；`error/close` 的重连只在 `if (options.autoConnect)` 下执行。
- `connection_pool.js:90-96`：`connect()` 是幂等的——`!isConnected() && !connecting` 才 `initiateConnection`，`connecting` 在 open/error/close 复位。
- `read.js:213-219`：`disconnect` / `connect` topic 在 busy 检查**之前**处理，所以读进行中也能接收 connect。
- `make_reconnect_change`（`flow_builders.py:729-747`）是**死代码**，且写的是 `topic=reinitialize`——当前 1.2.1 的 read.js 不认 `reinitialize`，不要恢复它。

**最小修复（二选一或都做）**

1. **生成器加 connect 心跳**：每 10–30s 发一条 `msg.topic='connect'` 到 MC Read；包内 `connect()` 幂等，断线时可重建。这是不改第三方包的最小方案。
2. **修包**：把 `options.autoConnect == "undefined"` 改成 `typeof options.autoConnect === "undefined"`，让默认值为 true；同时保留 connect 心跳作为兜底。改包需评估现场升级/回滚。

**验收**

- 拔网线 30s 再插回：10–30s 内恢复；日志无 uncaughtException。
- 停 PLC/关端口：持续重试但不过载；恢复后自动继续。
- 不要用 `reinitialize`。

**补充定论（10-18 复核，增量）**

1. **源码定论**：`read.js:213-220` 的 input 处理器只有 `disconnect`（→`closeConnection()`）和 `connect`（→`connect()`）两个 topic 分支；`reinitialize` 不在其中，会落到普通读取流程，不能重建连接。
2. **基线分层（Day 3-5 验证口径）**：driver 抽取相对**接手时工作区**通过（抽取前后一致）；相对 HEAD 的差异来自 **Day 0 前就有的未提交改动**（重连支路删除 + info 改"连接池自动重连" + golden 改动），不能归因于本次抽取。
3. **Day 7 方向**：用 `inject(30s) → change{topic:"connect"} → MC Read` 心跳替换旧死支路；同时把 info 里"连接池会自动重连"的错误表述一并改掉；**不恢复 `reinitialize`**。
4. **防止误判复发**：不得把"删除死支路"说成"删除有效重连"（`reinitialize` 本就无效）；也不得仅凭 canonical 自洽证明相对 HEAD 变化。golden 纪律：变更前先对拍基线、确认 diff 只含预期变化（connect 心跳 / info / 测试）；确认后 Day 7 属**有意功能变更，应重录 golden**（否则旧 golden 永远失败）；**禁止的是不检查 diff 就重录、用新基线掩盖非预期变化**。

### P0-3 类型与地址

**3.1 UINT16 没有前缀**

- `generator_service.py:34`：
  ```python
  _MC_TYPE_PREFIX = {'INT32': 'DINT', 'UINT32': 'DWORD', 'FLOAT': 'FLOAT', 'DOUBLE': 'REAL'}
  ```
  缺 `UINT16`。包解析格式是“设备 + 数据类型 + 地址”（`mcprotocol.js:3060-3145`），`UINT` 是 2 字节无符号（`enumDataTypes`：`D:/nodered/.../mcprotocol.js:2757-2762`）。所以正确地址是 `DUINT100`（设备 D + 类型 UINT + 地址 100）；当前 `D100` 会按 INT（有符号）解析。
- 最小修复：`_MC_TYPE_PREFIX['UINT16'] = 'UINT'`；黄金/冒烟加 `DUINT100` 断言和真机负值→正值用例。

**3.2 DOUBLE 不支持**

- `_WORDS_PER_TYPE['DOUBLE'] = 4`，但 `_MC_TYPE_PREFIX['DOUBLE'] = 'REAL'`；包内 `REAL` 的 `dataLength = 4`（2 字），不是 8 字（`mcprotocol.js:2757-2758`）。
- 结果：单点 DOUBLE 生成 `DREAL100,1`，只读 2 字，后面两字错位；块合并的 `items` 计算也按 4 字，和实际读 2 字不一致。
- 最小修复：**生成期明确拒绝 DOUBLE**，报“当前 MC 包不支持 8 字节 DOUBLE，请改用 FLOAT 或拆两个 32 位”；不要静默降级。若必须支持，需要真机验证 8 字节读取方案（包内没有现成 DOUBLE 类型）。

**3.3 地址进制/校验**

- `_validate_inputs`（`generator_service.py:101-139`）用 `int(addr)`：
  - 拒绝 `W/B/X/Y` 的十六进制地址（如 `1A`）；
  - 不区分 FX 的 X/Y 八进制；
  - `_merge_blocks` 排序也用 `int(t['register_address'])`（`generator_service.py:182`），十六进制地址会直接异常。
- `tag_service.py:56-90` 已有正确的进制规则：
  - `W/B` 及非 FX 的 `X/Y` → 十六进制；
  - FX 的 `X/Y` → 八进制；
  - 其余 → 十进制。
  生成器没有复用这套校验。
- 最小修复：抽一个 `_parse_addr(tag, device)`，按 `register_type + plc_series + protocol_params.octalInputOutput` 返回整数；校验、排序、合并、key 格式化全部用它。
- 注意：`tag_ref_expr` 的 `octal_xy` 分支（`flow_builders.py:496-497`）方向是对的（FX 八进制转十六进制字符串），但**只改了 lookup key，没改 MC Read 地址串**；FX 场景会读/查不一致。

**3.4 FX 支持要真机确认（重要）**

- 包 `enumPLCTypes` 只有 `A/QnA/Q/L/R`，**没有 FX**（`mcprotocol.js:2634-2640`）；生成器传 `plcType='FX'` 时，包会回落 Q 并打警告（`mcprotocol.js:172-180`）。
- `octalInputOutput` 选项在 `connection.js:54-56` 传入，但在 `init` 里**没有被使用**（全文件只有参数声明/传递，没有实际转换；`mcprotocol.js:3027` 的 `octalInputOutput` 参数在函数体内无引用）。X/Y 的 device spec 是 `Hexadecimal`（`mcprotocol.js:2680-2681`）。
- 结论：FX 的 X/Y 八进制目前没有可靠证据；生成器把 FX 当已支持是过度声明。最小处理：
  1. 生成期若 `plc_series` 是 FX 且存在 X/Y 点位，先真机探针验证；
  2. 探针不通过就**明确拒绝 FX X/Y**，不要生成“看起来能跑”的流；
  3. 若现场必须 FX，考虑在生成器把八进制地址转成包认可的十六进制/十进制写法，并同时修正读地址与 lookup key。

**3.4 补充定论（10-18 用户裁决：三地址域，勿再混判）**

FX X/Y 的进制不能只从探针单层判断，分三个域：

| 层次 | 示例 | 值 |
|---|---|---|
| 用户配置域（FX X/Y **八进制**，项目已确认契约） | `X17` | 八进制 = 15 |
| 生成器换算（八进制→十六进制下发） | `XF` | 十六进制 = 15 |
| 包地址域（包按**十六进制**解析） | `XF` | offset 15 |

- 换算链路 `X17 →(八进制) 15 →(十六进制) XF →(包) 15` 值一致，**方向正确，保留 `radix=8`（FX X/Y）与 `X17→XF`**，不能改成直接下发 `X17`。
- 探针里 `X17 → offset 23`（包直接吃未换算字符串）是「不换算会读错」的**反例证据**，不是「换算错误」的证据。
- 探针 FX 回落 Q（`requestedPlcType=FX → effectivePlcType=Q`），只能证明包如何解析字符串，不能否定 FX 的八进制业务约定。
- **FX 真机是独立验收门**：未真机验证前不得宣称 FX 生产可用；若发布策略要求「未见真机即禁止生成」，才需额外加生成期拒绝。
- 测试表达需加强：探针 `address` 字段明确为「MC 包输入地址」（非用户配置地址）；smoke 补正向链路断言（配置 X17→XF→包 15→key XF），并保留 `X17/X10/Y10` 作为「未经换算」的反例标注。

**3.5 字节序/字序未消费**

- `_validate_inputs` 检查同设备多字点位的 `byte_order/word_order` 一致性（`generator_service.py:126-136`），但生成的 MC Read 没有把这两个字段传给包；`_MC_TYPE_PREFIX` 也没有大小端参数。
- 结果：多字点位实际按包默认字节序解析，配置里的 byte/word order 只是“校验用”，不生效。
- 最小修复：真机确认包的字节序行为；若包不支持，生成期禁止配置非默认值，避免假承诺。

### P0-4 安全（4a/4b/4c/4d）

**4a PG 凭证在合并部署时丢失**

- `make_pg_config`（`flow_builders.py:438-455`）把 `user/password` 作为普通字段写入；`PgTargetModel` 明确写“内嵌生成文件，明文”（`flowgen_vo.py:20-21`）。
- 合并部署会摘掉旧生成 tab 和已知生成的全局 config 节点，再追加新 payload（`deploy_service.py:157-185`）。如果重新生成时 `pg_user/pg_password` 留空（常见），新的 PG config 节点没有账号密码，旧的手工录入值被替换掉。
- `_canon_norm` 又在漂移比对里忽略 `postgreSQLConfig` 的 `user/password`（`deploy_service.py:76-77`），所以漂移检测不会提示这个丢失。
- 最小修复：
  1. 部署前从 live flows 读取同 id 的 PG config，回填 `user/password`；或
  2. 把 PG 账号密码改为 Node-RED credential 类型（需要包支持/改包）；或
  3. 至少部署后在 UI 明确提示“PG 凭证需重新录入”，并禁止把密码写入版本链/快照。
- 这是发布门槛：不能“生成一次、部署一次就把密码弄丢”。

**4b 快照/版本/下载脱敏**

- PG 明文会进 flows.json、release payload、画布快照、flows-upload 的 LONGTEXT；下载接口把整个 flows.json 返回。
- 最小修复：读/下载时统一脱敏（PG password、MQTT password、X-API-Key）；部署时从独立的加密/凭证存储回填；快照标注敏感文件并限制访问。
- 注意 flows-upload 的下载 `media_type` 必须是 `application/octet-stream`，否则前端 `blobValidate` 误判；脱敏不能改变这个 header。

**4c Node-RED Admin API 没有 adminAuth**

- 边缘 1880 的 `GET /flows`、`GET /nodes`、`POST /flows`（含 credentials）默认无认证；`GET /flows` 直接泄露 PG 明文密码。
- 最小修复：启用 `adminAuth`，覆盖 `GET /flows`、`GET /nodes`、`POST /flows`、`POST /credentials`；生成器的部署客户端改用 Basic auth；site-health 的 flows-upload 也要带认证。
- 验收：未认证请求 401；部署、漂移检测、flows-upload 均正常；不要把 adminAuth 凭证写进 flows.json。

**4d 全局 X-API-Key**

- `monitor_controller.py:39-48` 只校验一个全局 `MONITOR_API_KEY`；任何拿到该 key 的人都能上报心跳/PG 计数/设备通信，也能读离线区间。
- `site_health_service.py:500-553` 的离线区间返回 `teamsWebhook`，全局 key 持有者可枚举/窃取 webhook。
- key 还会被生成进 flows（心跳支路），随 flows.json/快照/下载扩散。
- 最小修复（P1 可排期，但发布前至少做 redaction）：按现场独立 key、key 不返回给前端/不进快照、`teamsWebhook` 脱敏或只允许后端内部读取。

### P0-5 合并部署残留（孤儿）

**现象**

- 删除设备/点位、重命名 tab、把节点移出生成 tab 后，旧生成节点可能留在边缘，越积越多。

**证据**

- `_merge_flows`（`deploy_service.py:157-185`）的认门规则：
  - tab id ∈ `known_gen_ids`，或 label 以 `GEN_` 开头；
  - 节点 `z` ∈ 被删 tab id；
  - 全局节点 id ∈ `known_gen_ids`。
- `known_gen_ids` 只由“本次 payload + 最新 release payload”组成（`deploy_service.py:394-396`）。
- 因此：
  - 设备在**两个版本以前**被删：旧 id 不在最新 release，也不在本次 payload → 残留；
  - tab 被用户改名且 id 不在 known → 残留；
  - 生成节点被拖进用户 tab → `z` 不在生成 tab id，id 也不在 known → 残留；
  - 只改 tab 前缀/设备名导致确定性 id 变化 → 旧 id 残留。

**最小修复**

- 给所有生成 tab/节点加标记：`edgelink_gen: true`、`site_id`、`device_id`、`gen_version`。
- `_merge_flows` 改为：删除该 `site_id` 下所有带标记的 tab（以及 `z` 指向它们的节点），不再依赖 label/id 猜测。
- 首次切换做一次“旧规则清理 + 新标记写入”的兼容部署；`_canon_norm` 必须忽略这些标记字段，否则漂移检测永远不相等。
- 验收：删除设备后连续部署两次、改名 tab、移动节点，边缘都不残留；用户自建 tab 不受影响。

### P0-6 质量码/计数语义

**现象**

- `comm_expr` 只数 `BAD`（`flow_builders.py:503-509`）：
  ```python
  '($count(payload.values[quality="BAD"]) = 0) ? "true" : "false"'
  ```
- 块内缺失 key 时，`block_assemble_expr` 标 `UNCERTAIN`（`flow_builders.py:511-542`）；`UNCERTAIN` 不计入 BAD，所以设备仍显示在线。
- `final_assemble_expr` 的 `value_count = $count($vals)`（`flow_builders.py:619`）是**配置点位总数**，不是好值数；顶层 `quality` 也只在有 BAD 时为 BAD（`:621`），有 UNCERTAIN 时仍是 GOOD。
- 结果：MC 返回空/缺 key 时，下游看到“在线 + value_count=N + quality=GOOD”，但值全是 null/UNCERTAIN。

**最小修复**

1. `comm_expr` 改为：无 BAD、无 UNCERTAIN、`payload != null`、`!msg.problem` 才算在线；或明确“UNCERTAIN 不算离线”的产品决策并写进契约。
2. `value_count` 语义二选一：
   - 保持“配置点数”，另加 `good_count/bad_count/uncertain_count`；或
   - 改成“好值数”，并把字段名/文档同步改掉。
3. 顶层 `quality` 增加 UNCERTAIN（或 `DEGRADED`），但必须先确认下游（PG、MQTT、监控页、Teams）能接受新值；不要同时引入 UNCERTAIN 和 DEGRADED 两套。
4. 加真机用例：断线、单块失败、单点缺失、空数组，分别断言 `quality/value_count/comm`。

## 5. MC 位设备语义速查（用户特别强调）

### 5.1 两类设备，两套规则

| 类别 | 设备 | 地址含义 | `.bit` | 输出 key |
|---|---|---|---|---|
| 位设备 | `M L F V` | 位号（十进制） | **不允许/无意义** | `M200` |
| 位设备 | `X Y` | 位号（FX 八进制 / 非 FX 十六进制） | **不允许/无意义** | 按包要求进制大写 |
| 位设备 | `B` | 位号（十六进制） | **不允许/无意义** | `B1A` |
| 字设备 | `D W R` | 字地址；BIT 时另有 0–15 位号 | 允许 | `D100.3` |

### 5.2 `M200.3,4` 到底是什么

- 包解析：`M200.3,4` → 设备 M、地址 200、bitNo 3、count 4；因为 M 是位设备，`datatype=BIT`，`remainder = 200 % 16 = 8`，`requestOffset = 192`，`wordLength = ceil((8+4)/16) = 1`。
- 实际读：从字 192 开始读 1 个字，取其中 bit 8..11；这 4 个全局位是 **M200、M201、M202、M203**。
- `read.js` 输出：`M200`、`M201`、`M202`、`M203`（不是 `M200.3..M200.6`）。
- 因此：
  - **`M200.0,4` 和 `M200.3,4` 读到的全局点位都是 M200~M203**（`.0`/`.3` 对位设备不改变起始位）。
  - 不要再说“`M200.3,4` 读 4 个字”；它是 4 个位点，跨 1 个字。
  - 不要再说“实际是 M200.8~M200.B”；`8` 是字内位偏移，不是全局地址。

### 5.3 生成器的正确写法

- 位设备单点：`M200`。
- 位设备连续：`M200,4`（或 `M200.0,4` 也能读，但建议统一成 `M200,4`）。
- 位设备 key：`M200/M201/M202/M203`。
- 字设备单点：`D100`。
- 字设备位：`D100.3`。
- 字设备位连续：`D100.3,4` → key `D100.3..D100.6`。

## 7. 整改计划评审（含内部矛盾）

整体方向认同约 **85–90%**；P0 的拆分是对的。需要修正的地方：

1. **P0-6 的 `value_count` 与验收标准冲突**：如果改成“好值数”，下游/验收要同步；如果保持“配置点数”，必须另加 `good_count`，不能只改文档。
2. **P0-4d 的位置**：按现场独立 key 是 P1 可以，但“key 不进快照/不返回前端”属于 P0-4b 的脱敏范围，不能一起推到 P1。
3. **adminAuth 范围**：必须覆盖 `GET /flows`、`GET /nodes`、`POST /flows`、`POST /credentials`；只保护 `POST /flows` 不够，`GET /flows` 已经泄露 PG 密码。
4. **探针输入 vs 生成器输入**：探针要用“生成器实际会生成的地址串”和“手工期望 key”两组；否则探针通过但生成器仍错。
5. **首次 marker 部署**：P0-5 引入标记后，第一次部署要兼容旧规则（先按旧规则清理，再写标记），否则旧残留永远清不掉。
6. **`_canon_norm` 要忽略 marker 字段**：否则漂移检测会把 marker 当差异，永远不相等。
7. **`DEGRADED` 下游兼容**：如果引入第三态，先确认 PG（quality 列）、MQTT 消费者、监控页、Teams 都能处理；不要同时出现 `UNCERTAIN`/`DEGRADED` 两套。
8. **X-API-Key 脱敏/回填**：生成流里 key 是明文；脱敏后部署要能回填，否则心跳失效。

1. **72h 浸泡 vs 2 天**：Day 12–13 只有 48h。要么 Day 10 启动浸泡，要么明确改成 48h。

另外三个隐性缺口：
- **没有 Day 0**：工作区还有未提交改动，先冻结/基线/备份；
