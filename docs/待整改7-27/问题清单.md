## P0-1　32/64 位点位数据被死字段旁路：解码全对，入库全错

- **位置**：`mitsubishi-read.js:637-639,690,437-444`；`modbus-read.js:689-699,449`；`07_数据管道处理.js:159,175,182,231`
- **现象与证据**：协议节点把解码结果（含 32/64 位多字组装值）写入 `convertedValue`，但 emit 的 `rawValue` 永远是**第一个 16 位字**；下游 data-processor 只消费 `entry.rawValue`。`convertedValue` 在全部 17 个流程函数中 **0 引用**（grep 实证）。
- **风险**：当前生产全是 INT16/UINT16（首字即全值）所以数据正常；**一旦配置第一个 FLOAT32/INT32/UINT32/DOUBLE 点位，PG/MQTT 存的是该值的第一个字，quality 却标 GOOD**——静默错数据。触发条件：用户新建任一 32/64 位点位。
- **修复建议**：协议节点 emit 改为 `rawValue: entry.convertedValue`（保留原首字到 `rawWord` 备查），或 07 入口统一 `var v = entry.convertedValue ?? entry.rawValue`；两包同步改；补 FLOAT 端到端回归。
- **验收标准**：模拟器配 FLOAT32=23.5、DOUBLE=-1234.5678、INT32=70000、UINT32=4000000000 四个点位，PG 中 `eng_value` 与真值误差 <1e-4，quality=0。
- **验证方式**：代码逐段核实（emit/消费/死字段 grep）。

## P0-2　bootstrap 接入层：/auto 当前 100% 崩溃 + 双接口零鉴权

- **位置**：`module_plc/controller/bootstrap_controller.py:27-29,53-110,120-174`；`module_plc/entity/do/bootstrap_key_do.py:9-22`
- **现象与证据**：① 2026-07-27 19:48 实测：`GET /plc/config/bootstrap/auto?host_pc_ip=<任意>` 无 token 不返 401，但对任何输入 500：`'machine_fingerprint' is an invalid keyword argument for EdgeBootstrapKey`——controller 传了 DO 没有的字段，而 MySQL 表里该列存在（DDL 已核）→ ORM/库漂移，**新节点首次接入全灭**。② 双接口无 PreAuth（:27-29），框架无全局鉴权中间件；知道 IP:port 即可冒领 `secret_key`（:82-88），再经 `/plc/config/bootstrap` 换出 monitor_api_key + edge_collector 密码 + MQTT 凭据（:151-174）；secret 永久有效；fingerprint 分支可把节点 host_pc_ip 改写为调用方 IP（:53-71）。

- **修复建议**：DO 补 `machine_fingerprint` 列对齐库；`/auto` 仅首次注册发放 secret（已注册须凭 secret 或管理端重置）；secret 存哈希+有效期，换取正式凭据后作废；双接口加限流与网络 ACL；fingerprint 变更需管理端二次确认。
- **验收标准**：无 token 访问两接口返 401/403；新节点首次注册→换取凭据→心跳全链走通；已注册节点无法通过 /auto 再领 secret；错误日志无 500。
- **验证方式**：API 实测（崩溃）；鉴权缺失为代码核实。
