## 必须重点挑战的设计决策（逐条给出"合理/不合理+理由"）

1. **注册窗口（按压配对）**：新节点注册需管理端开 10 分钟窗口（Redis TTL），/auto 否则拒绝；Redis 故障 fail-closed。质疑点：运维便利性 vs 安全性是否平衡？fail-closed 会不会在 Redis 抖动时挡住合法节点？有没有更优模式（如审批制/预共享令牌）？
2. **secret 不作废**：边缘每次重启都凭 secret 重新 /bootstrap，因此放弃"换取后作废"，改用 哈希存储+窗口闸+限流+regenerate 轮换。这个取舍是否成立？残余风险是什么？
3. **告警"确认卡死"修复方案（Day 3 计划）**：`create_alert` 命中 status=1（已确认）且行龄超 90s 时重置 created_at 并重通知；resolve 覆盖 0/1。质疑点：这个"行龄阈值重开"会不会造成已确认告警的重复轰炸？有没有更好的状态机设计（如 episode id、last_notified_at 字段）？
4. **告警通知门控**（仅状态翻转才通知）：会不会漏掉"翻转瞬间 MQTT 断线"的通知？需要补偿机制吗？
5. **MC 节点 per-PLC 轮次闸**：同 PLC 上轮未完时新轮次直接失败丢弃（而不是排队）。这对"数据新鲜度"是对的，但对"调度公平性/监控误报"有没有副作用？
6. **写安全设计**：写分组严格连续（间隙拆组、绝不向未配置地址写 0）；位设备原生位写、字内位 RMW。这个设计有没有遗漏的破坏场景？
7. **密钥轮换但未清 git 历史、未轮换 DB 密码**（机主决定的延期项）：风险评估是否如实？延期是否可接受？
8. **EMQX 配置全在 mnesia（REST API 写入，无配置文件）**：服务重启持久，但机器迁移/备份怎么保证？是否应补一份声明式配置？
9. **10 天计划本身**：排期是否合理？有没有漏掉的整改项（审查清单之外的盲区）？试运行准入检查单有没有过松/过紧的项？
