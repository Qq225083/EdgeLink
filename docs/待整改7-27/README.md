## 审查结论摘要

- **能跑的部分**：当前生产形态（3E 帧 + 全 16 位点位 + 单边缘节点 + 内网）采集主链数据基本正确——PG 43649 行实证、3E 帧逐字节合规、调度/死区/强推链工作、spool 无积压、SQL 注入面干净、ORM 纪律良好。
- **不能投产的原因**（按主题）：
  1. **安全准入**：全部密钥随 git 入库（P0-5）；bootstrap 双接口零鉴权且当前 100% 崩溃（P0-2）；EMQX 匿名（P1-10）。
  2. **监控在说谎**：发布假成功（P0-3）；确认过的告警永久卡死——节点离线 8 天无告警实证（P0-4）；健康计数失真（P1-13）；告警风暴单日 590 次（P1-8）。
  3. **三颗已装填的定时炸弹**（全部"首个该类点位上线即静默错数据且 quality=GOOD"）：32/64 位解码被死字段旁路（P0-1）；4E 帧布局不符三菱规范（P0-7）；Q/L 系列 X/Y 进制错误 + Modbus CR/DISCRETE 功能码错（P1-3/P1-4）。

## 关键实测证据（一页速览）

- `flows.json` 线上副本与权威源 MD5 一致，无版本漂移；`tmp_extract/` 根目录 4 个副本已过期（审查已改用 `_current/` 新鲜提取）。
- 分页：camelCase `pageNum/pageSize` 全链生效；**snake_case 实测静默失效**（返默认 pageSize=10），仅 `/plc/tag/global/list` 做了手工兼容。
- 告警：`nodered_node` 56 离线 8 天，`NODE_OFFLINE id=13 status=1`（6-20 确认）卡死，30s 扫描静默跳过；孤儿 open 告警 4 条（node_id 999/4975/59/60）。
- 发布：`publish_by` 近 5 条全 NULL（`request.state.user` 从未赋值）；`device_ids` 常记字符串 'null'。
- 死区：DB 注释"ms"默认 1000 vs VO/前端/边缘按"数值"消费；PG 实证 deadband=1000 点位数据密度约为 deadband=0 的一半。
- 时序表：`edgelink.plc_data` 43649 行，**0 索引 0 约束**（ON CONFLICT 去重失效）；`pg_success_count=0` vs 实际近 2 天写入 16458 行。
- bootstrap：`GET /plc/config/bootstrap/auto` 无鉴权且对任意输入 500（ORM 缺 `machine_fingerprint` 列，库表有）。
- 凭据：仓库内旧流程文件硬编码的 PG 密码实测可连上生产 PG（任务书提供的密码反而是错的）→ 佐证"密钥入库"不是理论风险。

## 整改纪律

1. 每修一条，对照《问题清单.md》该条的"验收标准"实测打勾，不许"改完即算完"。
2. 两个协议 npm 包（MC/Modbus）**53% 逐字重复**，凡是连接池/解码类修复必须**双侧同步**，并优先沉到共享包。
3. 协议帧修复必须用 golden buffer 对拍（可用本机 `D:\nodered\data\node_modules\node-red-contrib-mcprotocol` 或 pymcprotocol 生成参照），不许只改不测。
4. 改库结构（死区列类型、plc_data 唯一索引）必须先备份 + 写迁移脚本 + 存量数据处理方案。
5. 密钥轮换当天协调好后端/边缘/前端同步切换，避免互相锁死。
6. 不要把任何真实密钥写进本目录文档；凭据一律引用 `.env` 位置，Day 1 统一轮换。
