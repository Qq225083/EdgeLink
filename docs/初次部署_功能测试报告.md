## 七、计算点位（2026-08-22 新增功能验收）

需求：某点位 = 同设备其他点位的 和/平均/最大/最小（派生/计算点位，边缘自治求值）。

实现面：DB 迁移（plc_tag +calc_op/calc_source_ids）→ 后端校验（算子/来源同设备/禁链式/设备至少有 1 个启用采集点位）→ 快照携带 → cm 分流（不进读取清单，挂设备级 calcTags）→ DP 求值（复用 换算/死区/变化触发/PG/MQTT 管道）→ 前端点位表单（采集/计算类型切换 + 来源多选）。

实测记录（设备 30，计算点位 id=69 = sum(tag59, tag60)）：
- 求值正确性：22:27:58 源 8743+527 → 计算 9270 ✓；22:27:56 源 -24282+805 → -23477 ✓（逐笔核对一致）
- 寄存器占位：registerType=CALC，不进 MC 读取清单 ✓
- 变化触发联动：设备 triggerKind=2 下，计算点位只在和变化时插入（连续相同值不插）✓
- 校验负向：非法算子/无来源/跨设备来源/来源不存在 全部正确拒绝 ✓
- api_smoke.py 已沉淀计算点位用例（建/读/改/删 + 非法算子拒绝），全量 60 PASS

注意（既有行为，非本次引入）：变化触发模式下，未变化的采集点位在 lastGood 缓存中会被标 UNCERTAIN，计算点位若引用它们，其结果质量位随之 UNCERTAIN（值为最近有效值，语义正确）。

另记录一处环境操作教训：08-22 晚设备 30 的 triggerKind 被 UI 编辑带回 1（当时浏览器是旧 bundle，禁用选项显示异常）。前端放开选项后需硬刷新，否则下拉对 value=2 显示为空——已在本轮环境恢复后验证新 bundle 正常。
- 变化判定过插修复（2026-08-23）：计算点位上一值改用 edge_lastCalc 独立跟踪（lastGood 只收 GOOD 质量位，UNCERTAIN 计算点位参照值会被冻结导致重复插入），修复后计算点位插入率与源点位变化率完全一致 ✓

## 九、寄存器类型与地址规则审查（2026-08-23）

**审查范围**：plc_driver 寄存器类型/数据类型/地址正则 + plc_protocol_compat 品牌/系列/通信方式映射 + 边缘地址解析链路（CM → MC 包）。

**正确的部分**：
- 三菱 MC 8 种软元件（D/W/R/X/Y/M/L/B）对 Q/L/iQ-R 正确；FX 子集（D/X/Y/M）正确（FX 无 W/R/L/B）
- 基恩士 KV / 欧姆龙 / 西门子走 Modbus TCP 时用 HR(/IR)——正确（这些品牌原生地址 DM/CIO/DB 在 Modbus 路径下本就映射到保持/输入寄存器）
- MC 数据类型矩阵（BIT/BOOL 位偏移、INT32+ 字节序/字序）合理
- MC 包自身的地址解析（系列感知：W/B 恒 hex、非 FX 的 X/Y hex、FX 的 X/Y octal）正确

**发现并已修复**：
- **P1（已修）**：CM 边缘组装的地址解析对 X/Y 一律按 8 进制——Q/L/iQ-R 的 X/Y 是 16 进制，Q 系列 X10 会被解析成 8（应为 16），而 MC 节点优先消费 CM 给的整数地址 → 位元件读错地址。修复：CM 对齐 MC 包 parseDeviceAddress 的系列感知逻辑，7 个用例（Q 的 X10→16、FX 的 X10→8、Y1F/W1F→31、D100、M7、FX 八进制含 8 拒绝）与 MC 包逐一核对一致。双侧流已同步并重启生效。

**待改进（不阻塞，列入排期候选）**：
- Modbus 驱动 registerTypes 含 `CR` 与 `COIL` 重复（同为线圈）；protocol_compat 里 Q/Siemens 的 Modbus 行也用了 CR。建议统一为 COIL（或删 CR）
- PLC_RS232C 行中 Omron/Siemens 的 driverCode=UNKNOWN——配了也采不到（边缘分流丢弃），建议隐藏或待串口驱动补齐
- 驱动 addressPattern 种子 `^[0-9]+$` 对 MC 的 X/Y hex 地址是误导（当前仅展示不强制，未拦用户输入）
- L/iQ-R 的 MC 寄存器子集偏保守（少 L/B/R），可按需扩展
