# 存量监控增强设计文档（2026-09-20）

> 配套变更说明见同目录 `变更说明.md`。本文档记录两条新链路的设计取舍，供后续维护/评审。

## 1. error 日志上报链路

### 采集：RED.log.addHandler 旁路钩子

- Node-RED ≥0.20 提供 `RED.log.addHandler(fn)`，可拦截全实例日志事件，是**不侵入采集流**拿到 error 的唯一正规途径（读日志文件则路径/滚动策略各异，不可靠）。
- 事件结构 `{ts, level, msg, ...}`：level 10=fatal、20=error；只收 `level <= 20`，并排除 `metric`/`audit` 类事件。
- **handler 内 try/catch 全包裹、绝不外抛**——handler 崩了会波及 Node-RED 日志主链路，这是写死的纪律。
- 老版本无 `addHandler` 时静默降级：不采 error，心跳主功能不受影响。
- redeploy 时 `close` 里 `removeHandler` 摘除，避免多次部署叠加多个 handler。

### 缓冲与发送：随心跳捎带，成功才清除

- 环形缓冲 20 条、单条截断 500 字（error 日志常含堆栈，必须防爆量）。
- 每次心跳取缓冲头部最多 10 条放 POST body `{"errors":[...]}`；**仅上报成功才 splice 已发部分**——失败保留、下次重发，做到不丢不重（后端不可达期间的错误恢复后补报，超缓冲则丢最旧）。
- **为什么 errors 走 body 而非 query**：列表型数据有 URL 长度上限，且会落进反代/网关访问日志（含错误内容），Key 之外的信息也不该进 URL。

### 后端：快照式存储，不做错误履历表

- `site_health_site.last_errors`（TEXT，JSON 数组）覆盖式更新：节点发空数组即清空。
- 不建错误履历表：监控页只需回答「这台最近有没有报错」，原始完整日志的权威来源仍是现场 Node-RED 日志本身；建履历表只会让表无限膨胀且与心跳履历职责重叠。
- 服务端二次截断（10 条 × 500 字）兜底，不信任节点自觉。

### 协议兼容

- `/report` 保留全部 query 参数 + 新增**可选** JSON body：旧 1.0.x 节点对新后端行为不变；新节点对旧后端 body 被忽略，心跳不受影响。

## 2. flows.json 上传链路

### 触发：编辑器按钮 → 节点 admin 接口

- 参照 inject 节点按钮机制：editor 侧 `button.onclick` 弹窗收集**必填上传原因**，POST 到节点注册的 `RED.httpAdmin` 路由 `/site-flows-upload/:id/upload`。
- 在案坑复用：老版本 httpAdmin 自定义路由可能没挂 body-parser，`req.body` 为 undefined → 实现 `readBody` 手动收流兜底。
- `RED.auth.needsPermission` 存在才挂权限中间件，老版本无 auth 不挂（现场旧实例多数未开 adminAuth）。

### 身份与限流：与心跳同一套

- 抽取 `_resolve_site_by_key` 供心跳/上传共用：key 哈希 → 启停 → IP 绑定 → 端口绑定，拒绝语义完全一致（节点侧红灯显示后端中文原因）。
- 上传是低频人工操作：在心跳限流（IP 600/分 + key 20/分）之上再加 **每 key 5 次/小时**，防误触连点或脚本刷库。

### 存储：DB LONGTEXT，每站点留最近 5 份

- 不落盘文件：后端多实例/换机部署时文件会丢，DB 最省心；flows.json 通常几百 KB~几 MB，LONGTEXT 足够。
- 裁剪在写入**同事务**内完成（按 id 倒序留 5），无需新定时任务。
- SHA-256 由节点计算、后端复核：不一致直接拒绝（传输损坏早发现），并随记录存储供下载后比对。

### 下载

- 管理端 `GET /site/{siteId}/uploads/{uploadId}/download`，DAO 强制 `site_id` 归属条件防越权。
- **media_type 必须 octet-stream 而非 application/json**：前端 `blobValidate` 会把 json 响应当错误信封解析，文件会被误判为下载失败。
- 文件名 `flows-site{siteId}-{yyyyMMddHHmmss}.json`，经 `download-filename` 响应头传给前端 saveAs。

## 3. 共享配置节点

- 新增 config 节点 `site-health-server`（category: config，不进调色板，出现在配置节点侧栏），两个功能节点经 `serverRef` 引用。
- site-health 保留旧字段作回落：未选 `serverRef` 时用节点自身 server/port/basePath/https/credential key —— **已部署现场节点升级后零迁移成本**。
- site-flows-upload 为新节点，直接强制要求共享配置（`required: true`），新节点没有历史包袱。
